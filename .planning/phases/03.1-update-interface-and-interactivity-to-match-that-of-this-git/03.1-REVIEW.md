# Phase 03.1: Code Review Report

**Reviewed:** 2026-05-13T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

This phase introduces the monocle-style Ink TUI: `CandidateSelect`, `Modal`, `SearchInput`, `ControlsLine`, and `LoadingSpinner`, along with updates to `run-foreground.ts` that wire the TUI into the LLM result path. The shell contract and daemon bootstrap are unchanged and carry over clean from Phase 01.

The code is generally well-structured, but three blocking issues were found: (1) `onSelect` / `onCancel` callbacks in `CandidateSelect` are declared synchronous but called with async implementations in `run-foreground.ts`, creating an unhandled promise that silently drops the shell result; (2) pressing Enter on an empty filtered list passes `undefined` to `onSelect`, writing `undefined` to the shell buffer; and (3) the `ink` mock in `client-result.test.ts` calls `onSelect` with a candidate that does not exist when the test forces the initial `null` candidates render, meaning the LLM-mode test never actually exercises the rerender path.

## Critical Issues

### CR-01: `onSelect`/`onCancel` type mismatch — async callbacks silently drop promise

**File:** `src/ui/CandidateSelect.tsx:17-18` and `src/client/run-foreground.ts:145-156`

**Issue:** The `Props` interface declares `onSelect` and `onCancel` as synchronous:

```ts
onSelect: (command: string) => void;
onCancel: () => void;
```

But in `run-foreground.ts` both callbacks are `async` functions that call `await writeShellResult(...)` before `unmount?.()`:

```ts
onSelect: async (command: string) => {
  await writeShellResult(resultFile, { ... });
  unmount?.();
},
onCancel: async () => {
  await writeShellResult(resultFile, { kind: 'cancel' });
  unmount?.();
},
```

The `useInput` handler in `CandidateSelect` calls these callbacks synchronously. Because TypeScript widens `async () => void` to the declared `() => void`, the async function is called but its returned `Promise` is never awaited. If `writeShellResult` fails, the error is silently swallowed and `unmount` may never be called, leaving the modal frozen and the shell waiting forever on a result file that was never written.

**Fix:** Either declare the prop types as returning `Promise<void>` so callers are aware they return a promise, and await them inside `useInput`, or keep the callback synchronous and fire-and-forget intentionally with explicit error handling:

```ts
// Option A — type the props correctly
interface Props {
  onSelect: (command: string) => Promise<void> | void;
  onCancel: () => Promise<void> | void;
}

// And in the useInput handler:
if (key.return && candidates) {
  const visible = filterCandidates(candidates, query);
  void (onSelect(visible[selectedIndex]?.command ?? visible[0]?.command));
  return;
}
```

Or, in `run-foreground.ts`, move the async work outside the callback and use a resolved flag to signal completion without making the callback async.

### CR-02: Enter on empty filtered list passes `undefined` to `onSelect`

**File:** `src/ui/CandidateSelect.tsx:89-91`

**Issue:** When the live search query filters all candidates out, `visible` is an empty array. The Enter handler then evaluates:

```ts
onSelect(visible[selectedIndex]?.command ?? visible[0]?.command);
```

Both `visible[selectedIndex]` and `visible[0]` are `undefined` when `visible.length === 0`, so `undefined?.command` is `undefined`, and the `??` fallback also yields `undefined`. This calls `onSelect(undefined as unknown as string)`, which then writes `lbuffer: undefined` to the result JSON. The zsh widget reads that value into `LBUFFER`, clobbering the shell buffer with the literal string `"undefined"`.

The UI correctly renders a "no matches" message in this state, so the user can see there are no results, but the keyboard handler has no matching guard.

**Fix:** Guard the Enter handler against an empty visible list:

```ts
if (key.return && candidates) {
  const visible = filterCandidates(candidates, query);
  if (visible.length === 0) return;           // ← add this guard
  onSelect(visible[selectedIndex]?.command ?? visible[0]?.command ?? '');
  return;
}
```

### CR-03: `ink` mock in LLM-mode test calls `onSelect` before `rerender` — test does not cover the actual code path

**File:** `tests/client-result.test.ts:56-75`

**Issue:** The `ink` mock fires `onSelect` immediately from within the initial `render()` call, using `element.props.candidates?.[0]?.command`:

```ts
render: vi.fn().mockImplementation((element) => {
  const { onSelect, candidates } = element.props;
  if (onSelect) {
    Promise.resolve().then(() => {
      onSelect(candidates?.[0]?.command ?? 'git status');
    });
  }
  return { unmount: vi.fn(), rerender: vi.fn() };
}),
```

In `run-foreground.ts`, the initial render is always called with `candidates: null` (loading state). So `candidates` in the mock is always `null`, `candidates?.[0]?.command` is `undefined`, and the mock falls back to the hardcoded `'git status'` string. The `rerender()` call that would inject the real fetched candidates never runs the `onSelect` callback — the callback was already triggered. The test therefore asserts that the file contains `lbuffer: 'git status'` but this is the hardcoded fallback, not a result derived from the mocked `fetchCandidates` response. The test passes even if `rerender` is never called or the fetched candidates are completely wrong.

**Fix:** The mock should capture the `rerender` callback so it can trigger the post-fetch flow, or the mock should capture the `onSelect` from the rerendered element rather than the initial render. At minimum, assert that `fetchCandidates` was called and that `rerender` was called with a non-null candidates array:

```ts
it('emits a replace-buffer result in llm mode ...', async () => {
  const { fetchCandidates } = await import('../src/providers/claude.js');
  vi.mocked(fetchCandidates).mockResolvedValue([{ command: 'git status', explanation: '' }]);

  // ...run the client...

  expect(vi.mocked(fetchCandidates)).toHaveBeenCalledTimes(1);
  // Check rerender was called with the resolved candidates:
  const inkMod = await import('ink');
  const rerenderMock = vi.mocked(inkMod.render).mock.results[0]?.value?.rerender;
  expect(rerenderMock).toHaveBeenCalled();
});
```

## Warnings

### WR-01: Down-arrow on a single-item list divides by zero (effectively)

**File:** `src/ui/CandidateSelect.tsx:82-85`

**Issue:** When the filtered list has exactly one entry, pressing the down-arrow calls:

```ts
setSelectedIndex((i) => (i + 1) % visible.length);
```

`visible.length` is 1, so `(0 + 1) % 1 === 0` — this is mathematically safe (no divide-by-zero). However, if `visible.length` is 0 (which can happen due to a race: the key event is processed against the stale `query` captured in the closure at the top of `useInput`), then `(i + 1) % 0 === NaN`, and `setSelectedIndex(NaN)` is called. This won't crash immediately but will corrupt `selectedIndex` state and cause `visible[selectedIndex]` to return `undefined` on the next render or Enter key. The same applies to the up-arrow case at line 78.

**Fix:** Add an empty-list guard before computing modulo in both arrow handlers:

```ts
if (key.upArrow && candidates) {
  const visible = filterCandidates(candidates, query);
  if (visible.length === 0) return;
  setSelectedIndex((i) => (i === 0 ? visible.length - 1 : i - 1));
  return;
}

if (key.downArrow && candidates) {
  const visible = filterCandidates(candidates, query);
  if (visible.length === 0) return;
  setSelectedIndex((i) => (i + 1) % visible.length);
  return;
}
```

### WR-02: `selectedIndex` is not clamped when query narrows the list

**File:** `src/ui/CandidateSelect.tsx:49-56`

**Issue:** `selectedIndex` is reset to 0 only when `candidates` (the prop) changes, via the `useEffect`. It is never reset when `query` changes. If the user has moved the selection to index 3 in a list of 5, then types a character that narrows the list to 2 items, `selectedIndex` remains 3. The render then evaluates `active = index === selectedIndex` — no item renders as active because index 3 does not exist in the two-item visible list. On Enter, `visible[3]` is `undefined`, triggering the CR-02 scenario.

**Fix:** Reset `selectedIndex` to 0 whenever the query changes, or clamp it during render:

```ts
// Option A — clamp during render (no extra state/effect)
const visible = filterCandidates(candidates, query);
const clampedIndex = Math.min(selectedIndex, Math.max(0, visible.length - 1));
// use clampedIndex wherever selectedIndex is used in the render
```

### WR-03: TTY stream created from the same fd as the file handle — both writable streams race on close

**File:** `src/client/run-foreground.ts:117-124` and `src/client/run-foreground.ts:194-196`

**Issue:** `ttyHandle` is opened via `fsp.open('/dev/tty', 'r+')`. Then `tty.ReadStream` and `tty.WriteStream` are both constructed on `ttyHandle.fd`. When the modal finishes and `app.unmount()` is called, Ink may internally close or destroy those streams. The `finally` block then calls `ttyHandle.close()` on the same underlying file descriptor. Closing an already-closed fd produces an `EBADF` error at the OS level. Node's `fs.FileHandle.close()` does not check whether the underlying fd was closed by a different code path. In a zsh widget session this surfaces as an unhandled rejection logged to the terminal.

**Fix:** Track whether Ink closed the stream and skip the redundant close:

```ts
let ttyOwned = true;
ttyReadStream.once('close', () => { ttyOwned = false; });
// ...
finally {
  if (ttyOwned) await ttyHandle.close();
}
```

Alternatively, construct the `tty.ReadStream`/`tty.WriteStream` with `{ fd, readable: true }` and explicitly call `destroy()` before `ttyHandle.close()` to ensure orderly teardown.

### WR-04: `Modal` horizontal separator does not account for Unicode width of border glyphs

**File:** `src/ui/Modal.tsx:11` and `src/ui/Modal.tsx:19`

**Issue:** The separator line is computed as:

```ts
const innerWidth = width - 4;
// ...
<Text dimColor>{'─'.repeat(innerWidth)}</Text>
```

The subtraction of 4 accounts for: 2 border characters on the sides + 2 padding characters from `paddingX={1}`. However, `ink`'s `borderStyle="round"` renders the border using box-drawing characters that each occupy exactly 1 terminal column, and `paddingX={1}` adds 1 space on each side. So the inner content area is `width - 2 (borders) - 2 (padding) = width - 4`, which is correct for ASCII. The issue is that when `width` is set to a value that causes the separator to exceed the visible terminal width (e.g., terminal narrower than 80 cols), the separator line will wrap, breaking the visual layout. There is no terminal-width awareness. While this is not a crash, it means users on terminals narrower than 80 columns will see broken layouts.

This is a design limitation worth documenting, but should be addressed before general use since the default `width=80` will overflow on narrower terminals without any fallback.

**Fix:** Cap the modal width to the terminal's actual column count:

```ts
import { useStdout } from 'ink';
// ...
const { stdout } = useStdout();
const effectiveWidth = Math.min(width, stdout?.columns ?? width);
const innerWidth = effectiveWidth - 4;
```

### IN-01: `LoadingSpinner` animation frames array has a logical inconsistency

**File:** `src/ui/LoadingSpinner.tsx:4`

**Issue:** The FRAMES array is:

```ts
const FRAMES = ['thinking…', 'thinking.', 'thinking..', 'thinking…'];
```

Frames 0 and 3 are identical (`'thinking…'`). This makes the animation cycle through 4 frames but only display 3 visually distinct states. The intended progression appears to be `'thinking.'` → `'thinking..'` → `'thinking…'` cycling, but the array starts on the ellipsis and ends on it again, shortening the perceived animation. This is cosmetic, not a crash, but the duplication looks unintentional.

**Fix:**
```ts
const FRAMES = ['thinking.', 'thinking..', 'thinking…'];
```

### IN-03: `tsconfig.json` includes test files in the root compilation unit

**File:** `tsconfig.json:20`

**Issue:**

```json
"include": ["src/**/*.ts", "src/**/*.tsx", "tests/**/*.ts", "tests/**/*.tsx", ...]
```

Test files that use `vi.mock` and other Vitest globals are included in the main `tsconfig`. Because `"types": ["node"]` is set (not `["node", "vitest"]`), TypeScript will fail to resolve `describe`, `it`, `vi`, etc. as globals unless Vitest's own type declarations are also referenced. This can produce a confusing situation where `tsc --noEmit` passes with `skipLibCheck: true` but an IDE type-check shows errors in the test files. Separate test files into a `tsconfig.test.json` that extends the root and adds `"types": ["node", "vitest/globals"]`, or use triple-slash references inside test files.
