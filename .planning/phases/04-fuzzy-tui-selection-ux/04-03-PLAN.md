<objective>
Add top-level uncaughtException and unhandledRejection handlers to main.ts so
that any fatal error that escapes the run-foreground.ts try/catch still writes
{kind:'cancel'} to the FIFO before the process exits. Without this, a crash
before or after the Promise block would leave the zsh widget blocking on the
FIFO read for up to 30 seconds.

Purpose: Closes RUN-02 Pitfall 3 from the Phase 4 research. The resolved flag
in run-foreground.ts handles races within the Promise block; the handlers in
main.ts cover crashes that escape the Promise block entirely.

Output: src/cli/main.ts with process.on('uncaughtException') and
process.on('unhandledRejection') registered before the isDirectRun guard. The
handlers read QQ_RESULT_FILE from the environment, write cancel if set, then
re-exit. No other files changed.
</objective>

From src/cli/main.ts (current structure):

  export async function main(argv = process.argv.slice(2)): Promise<void> { ... }

  const isDirectRun = process.argv[1]
    ? import.meta.url === new URL(`file://${process.argv[1]}`).href
    : false;

  if (isDirectRun) {
    void main().catch((error: unknown) => {
      const message = error instanceof Error ? error.message : String(error);
      console.error(message);
      process.exitCode = 1;
    });
  }

The existing .catch() on main() handles errors from the async main() chain.
It does NOT handle errors thrown synchronously from Ink internals, React render,
or any void async call that rejects after the Promise resolves.

From src/client/result-writer.ts:
  export async function writeShellResult(resultFile: string, result: ShellResult): Promise<void>

Shell contract: the zsh widget passes the FIFO path as --result-file to the
qq client process. The qq client reads it from the CLI option. A safe way to
make it available to the top-level handler is via an env var QQ_RESULT_FILE
that the zsh widget sets before calling `zellij run ... qq client`.

Check shell/zsh/qq.zsh to confirm whether QQ_RESULT_FILE is already exported
or whether the handler should instead use a module-level variable populated by
runForegroundClient before the handlers could fire.

Alternative (simpler, no shell change needed): use a module-level
`let pendingResultFile: string | undefined` in main.ts. Set it from within
runForegroundClient by exporting a setter, OR read the --result-file CLI
argument before calling main() and store it. But modifying run-foreground.ts
interface is out of scope for this plan (files_modified: [src/cli/main.ts] only).

Simplest safe approach: register the handlers in main.ts; the handlers check
process.env['QQ_RESULT_FILE']. The zsh widget must export this env var before
the zellij run invocation. Read shell/zsh/qq.zsh to verify whether the export
already exists or needs adding — if qq.zsh needs changing, add it to
files_modified and update the plan accordingly.

Key constraint: writeShellResult is async; the uncaughtException handler must
fire-and-exit. Use synchronous fs.writeFileSync as a fallback since the handler
cannot await. Alternatively, call writeFile(...).finally(() => process.exit(1))
but synchronous is safer to guarantee the write completes before exit.
</interfaces>

  <action>
    Add two process event handlers to src/cli/main.ts. Place them after the
    existing imports and before the main() function declaration.

    The handlers must:
    1. Read the FIFO path from process.env['QQ_RESULT_FILE'].
    2. If the path is set and not empty, attempt a synchronous write of
       {"kind":"cancel"}\n to that path using fs.writeFileSync from 'node:fs'
       (which is already available in the runtime). Wrap the writeFileSync in a
       try/catch so a write failure (e.g. FIFO reader already gone) does not
       cause an infinite error loop.
    3. For uncaughtException: log the error to stderr, then call process.exit(1).
    4. For unhandledRejection: log the reason to stderr, then call process.exit(1).

    Import 'node:fs' at the top of main.ts for the synchronous writeFileSync.

    The handlers are registered at module evaluation time (top-level, not inside
    main()). This means they fire even if main() throws synchronously before
    registering the async catch. Do not use appendDebugLog inside the handlers
    (it is async and would itself throw in the handler context). Use console.error
    for the message.

    The reason for synchronous writeFileSync (not async writeShellResult): the
    uncaughtException handler is synchronous; awaiting async operations inside it
    is unreliable. writeFileSync is safe for FIFO paths on Linux/macOS — the
    kernel buffer will accept the small JSON payload synchronously.

    Do not add fenced code blocks here. The exact function signature and module
    structure are in the read_first file.
  </action>
