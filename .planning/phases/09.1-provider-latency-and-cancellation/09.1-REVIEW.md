## Summary

This is an incremental re-review of `6dd5220..HEAD`, limited to gap-closure plan 09.1-10 (the CR-01 fix). Changes that landed in the same range but belong to another task were not reviewed: the release workflow, CHANGELOG, `.releaserc.json`, `scripts/semantic-release-user-notes.ts` and its test, and `tsconfig.json`. Both in-scope test files pass (91 tests).

**CR-01 is resolved and verified for the events Ink delivers separately.** I traced the fix against the installed Ink 7.0.1, React 19.2.0 and react-reconciler 0.33.0:

- Ink renders with `LegacyRoot` by default. In this reconciler, `scheduleUpdateOnFiber` only calls `ensureRootIsScheduled`; it does not flush synchronously. `discreteUpdates` only sets the priority. So every event that `handleReadable` parses out of one read runs before any render. All of them run through the `useEffectEvent` impl of the last committed render, which means they all share one `renderToken`.
- The snapshot is valid only while that token matches. Any render that commits brings a new handler with a new token, and the closure state of that render already includes the queued edits. A render-phase arrival adjustment (the WR-06 clamp, or keeping the highlight by key) also produces a new token, so a stale snapshot never wins against the arrival block.
- A render that bails out (for example Down then Up in one read, where the final state equals the committed state) keeps the old handler and token. The snapshot then equals the committed state, so the result is still consistent. A scratch probe confirmed this: `Down Up` in one read, then `Down`, inserts row 1.
- StrictMode double render: each invocation makes its own token and its own handler, and the refs are shared. Whichever invocation commits has a matching pair. This is safe.
- WR-05 still holds: Backspace on an empty `live.query` returns before `applyInput`, so the highlight does not move. The invariance table covers this case.
- The new tests really do deliver keys in one chunk. Each `press` is a single `stdin.push`, which Ink reads as one chunk, and the mocked tests call one captured handler several times. Every new test would fail on the pre-fix closure-state code.

**The fix does not deliver the invariance it claims.** The new comment (lines 144-146) says "a key sequence gives the same result however stdin chunks it". Ink's parser splits a chunk only at escape sequences and DEL/BS bytes. `\r` and `\t` stay inside a text run, so typed text followed by Enter or Tab in one read becomes filter text. The invariance tests avoid this case on purpose (see the comment above `INVARIANCE_ROWS`) instead of fixing it. Details are in CR-02.

Prior findings outside this diff are carried forward unchanged and still open. I confirmed that `src/providers/**`, `src/cli/**` and `src/daemon/**` have no changes since `6dd5220`.

### CR-02: Enter or Tab typed in the same stdin read as text goes into the filter as an invisible control character, and Enter stops working

**File:** `src/ui/CandidateSelect.tsx:329-332` (claim at `:144-146`); `tests/candidate-select-layout.test.tsx` (comment above `INVARIANCE_ROWS`)
**Issue:** Ink 7's `input-parser.js` `splitBackspaceBytes` deliberately does not split `\r` or `\t` out of a text run ("they can legitimately appear inside pasted text"). One read of `ls\r` therefore reaches `useInput` as a single event, `input = 'ls\r'`. `parseKeypress` does not recognise that as `return`, so `key.return` is false. The handler falls through to `input && !key.ctrl && !key.meta` and appends `ls\r` to the query.

`filterCandidates` then matches nothing, because no command contains `\r`. Ink drops the CR when it draws, so the user sees `FILTER: ls` above `no matches — try a different query`. Every later Enter is a no-op because `visible.length === 0`. The only way out is a Backspace, which deletes the invisible character. `\t` behaves the same way, so `fd\t` toggles nothing and filters on `fd\t`.

I confirmed this with a scratch real-Ink probe that used the same FakeStdin/FakeStdout pattern, ran outside tracked sources, and has since been deleted:

- `press('ls\r')` as one read gave no selection, the frame `FILTER: ls` plus `no matches`. The same keys sent one per read inserted `ls -la`.
- Mounted loading, `press('log\r')`, then rows arrive gave no selection, `no matches`, and a further `press('\r')` still gave no selection.
- `press('\u007F')` followed by `press('\r')` inserted `ls -la`, which shows that a hidden CR was the cause.
- `press('fd\t\r')` on a flagged row gave no selection and `FILTER: fd`.

This is the same class of failure as CR-01: the result depends on how stdin chunks the keys. It is also the most common coalesced sequence. The zsh instant frame paints before Node starts, and G-09.1-5 invites typing while `thinking…` shows. Keys typed during Node startup sit in the TTY buffer and reach Ink as one read, so a fast `log⏎` hits this path. The ssh, Zellij and tmux PTY batching cited in CR-01 also applies. The comment at lines 144-146 promises a guarantee that the code does not provide, and the test suite was written around the gap instead of covering it.
**Fix:** Split text runs at `\r` and `\t` in the handler before dispatching. Use the snapshot so every piece composes (the handler is a closure over `live`, so recursion stays within the same read):

```ts
// At the top of the useInput callback, after `live` is computed:
if (input.length > 1 && !key.ctrl && !key.meta && /[\r\t]/.test(input)) {
  // Ink keeps CR/Tab inside a text run (paste rule); replay them as their own keys (CR-02).
  for (const part of input.split(/([\r\t])/)) {
    if (part === '') continue;
    handleKey(part, {
      ...key,
      return: part === '\r',
      tab: part === '\t',
    });
  }
  return;
}
```

To do this, move the handler body into a local `handleKey(input, key)` that re-reads `pendingInput` each time it is called. It must not capture `live` once per outer call, so that each part sees the previous part's edits. Also consider stripping any remaining C0 control characters (`/[\x00-\x1f]/g`) from text before appending it to the query, so that no invisible byte can make the filter unmatchable. A pasted `\n` is the same problem. Then add `ls\r`, `log\r` (typed during loading, before rows arrive) and `fd\t\r` rows to `INVARIANCE_ROWS` in their natural one-read form, delete the comment that says CR/Tab must be separated by an arrow or DEL, and correct the claim at lines 144-146 if any case is still left out.

## Warnings

### WR-01 (carried forward, still open): SDK fail-closed covers only `max_tokens`; a streaming `refusal` (or `pause_turn`) fragment still becomes a command

**File:** `src/providers/claude.ts:262-280`
**Issue:** The WR-07 fix branches on `message.stop_reason === 'max_tokens'` only (still at line 268). A streaming `refusal` or `pause_turn` stop also leaves partial text, such as `[{"command": "rm -rf`. When there is no strict list and no streamed row, that text reaches `parseCandidates`. `JSON.parse` fails, and the prose fallback offers the fragment for insertion into the shell buffer.
**Fix:** Treat every stop reason other than `end_turn` and `stop_sequence` as truncated:

```ts
const finishedNormally =
  message.stop_reason === 'end_turn' || message.stop_reason === 'stop_sequence';
// …
} else if (!finishedNormally) {
  const complete = completeCandidates(text);
  if (complete.length === 0) {
    void appendDebugLog('provider', 'response truncated', { model, stopReason: message.stop_reason });
    throw new Error(TRUNCATED_RESPONSE_MESSAGE);
  }
  finalList = complete;
}
```

Add a test that uses `stopReason: 'refusal'` and the fragment `[{"command": "find . -name`.

### WR-02 (carried forward, still open): Daemon shutdown with no open connection exits at once, cancelling the SIGKILL backstop it just armed for the retired idle child

**File:** `src/cli/commands/daemon.ts:45-64` (with `src/providers/claude-prewarm.ts:84-105`)
**Issue:** `shutdownDaemon` calls `disablePrewarm()` (line 52), which sends EOF to the idle child and arms an **unref'd** SIGKILL timer. It then waits out the grace period only when `connections.size > 0` (line 53). On the common path, an idle daemon with an idle prewarmed child, `process.exit(0)` runs long before the 1500 ms backstop fires. A child that ignores EOF or hangs (for example after laptop sleep) is left behind. The same is true for post-result or `terminateChild` kill timers whose connection has already closed.
**Fix:** Base the grace on live children, not on sockets. Have `disablePrewarm` return whether it retired a running child, and wait when either value is true:

```ts
const retiredIdle = disablePrewarm();
const inFlight = connections.size;
server.close(() => {
  if (inFlight === 0 && !retiredIdle) { exit(); return; }
  setTimeout(exit, graceMs);
});
```

A stricter option is a registry of children with pending kill timers, with exit once it is empty or the grace period has passed. Add a test that uses the `ignore-eof` fixture with no connection open.

## Info

### IN-01 (carried forward, still open): A second shutdown signal cuts the kill grace short

**File:** `src/cli/commands/daemon.ts:95-102`
**Issue:** SIGTERM and SIGINT are registered separately with `process.once` (lines 101-102). A Ctrl-C followed by a SIGTERM runs `shutdownDaemon` twice. On the second run, `server.close` fails with `ERR_SERVER_NOT_RUNNING` and `connections.size` is 0, so `exit()` runs during the first run's grace period.
**Fix:** Add a module-level `let shuttingDown = false;` guard and return early when it is already set.

### IN-02 (carried forward, still open): The WR-01 byte-cap regression test only tells old and new code apart when the OS splits the write into small reads

**File:** `tests/daemon-fetch.test.ts` (`measures the 256 KB request limit in bytes, not UTF-16 code units`)
**Issue:** The test writes the remaining ~269 KB in one `write`. If the kernel delivers that as a single read, the old code also rejects it, so the test passes without the fix.
**Fix:** Write the payload in explicit slices of about 4 KB, with `setImmediate` between them.

### IN-03 (carried forward, still open): The init deadline SIGTERMs a warm child that has been idle a long time, before it sends `init`; whether that interrupts a credential refresh is unverified

**File:** `src/providers/claude-cli.ts:25-38`, `src/providers/claude-process.ts:414-436`
**Issue:** `initDeadlineMs` sends SIGTERM to a prewarmed child that has been idle a long time and has not emitted `init` within 1500 ms. That is the most likely moment for an OAuth refresh. Nothing shows whether Claude Code refreshes the token before or after `init`.
**Fix:** In the WR-02 UAT, check with `QQ_DEBUG` stage logs that the first warm `??` after a sleep longer than the token lifetime logs `cli init` before any network-dependent delay. If it does not, raise `WARM_INIT_DEADLINE_MS` or move the deadline to the first `stream_event`.

### IN-04: The handler keeps processing keys after accept or cancel within one read, so `onSelect` can fire twice with different commands

**File:** `src/ui/CandidateSelect.tsx:282-285, 317-327`
**Issue:** After `onSelect` or `onCancel`, later events from the same read still run through the handler. Because the snapshot now carries the moved highlight, `Down ⏎ Down ⏎` in one read calls `onSelect('git log')` and then `onSelect('ls -la')`. I confirmed this with the scratch probe. Before the fix, both calls would have carried the same command. Production is protected only because `run-foreground.ts:294` guards with `resolved`. The component itself does not enforce "accept at most once", so any other host, or a future refactor of that guard, would see two inserts or an insert after a cancel.
**Fix:** Mark the input as finished in the snapshot, or in a `useRef(false)`, when Enter or Esc fires, and return early at the top of the handler once it is set:

```ts
const finished = useRef(false);
// in the handler, first line:
if (finished.current) return;
// before onCancel() / onSelect(...):
finished.current = true;
```
