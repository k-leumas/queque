# Phase 09.1: Code Review Report

**Reviewed:** 2026-10-12T08:00:18Z
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

I reviewed the stream-json runner, the prewarm pool, the candidate scanner, the CLI/SDK adapters, the daemon IPC (server, client, bootstrap), the foreground client, and the streamed-row UI state in CandidateSelect.

The core child-lifecycle code in `runClaudeTurn` holds up under tracing:
- Every exit path goes through `finish()`, so the turn settles once.
- The abort listener is removed on settle.
- Every `result` arms the backstop, and every abort, timeout or overflow calls `terminateChild`.
- An `is_error` result never reaches `parseCandidates`; its text only goes out as the failure's `stdout`, which feeds the auth regex.
- The prompt is on stdin. Stage logs carry only `ms`, `warm`, `code` and `signal`.

I found no blocker. The main defects:
1. **Daemon UTF-8 decoding (WR-01).** The daemon still decodes IPC input chunk by chunk. A probe confirmed it: a 60 KB envelope came in as 8 chunks and had 12 U+FFFD replacement characters. The phase fixed this only on the client side.
2. **Hung warm child (WR-02).** A warm child that hangs, rather than exits, gets no cold retry. It uses up the whole 25 s budget, which is the laptop-sleep case the retry was written for.
3. **Daemon shutdown (WR-03).** Shutdown leaves the pool enabled, so an in-flight query's `finally` respawns a prewarm child after `retirePrewarmed()`.
4. **CandidateSelect state under streaming (WR-04 to WR-06):**
   - The first row alone decides whether to clear a typed query.
   - The `[query]` effect undoes the keep-highlight-by-key logic.
   - NaN or -1 indices survive new rows arriving.
5. **SDK truncation (WR-07).** The SDK path keeps `max_tokens: 1024` while effort can now be set up to `max`. A truncated answer with no closed object goes through the prose fallback, and the raw JSON fragment becomes the command.

## Warnings

### WR-01: Daemon decodes IPC bytes per chunk, so split UTF-8 characters in the envelope are corrupted

**File:** `src/daemon/server.ts:48-53`
**Issue:** `buf += chunk.toString()` decodes each socket chunk on its own. On macOS a Unix-socket write over 8 KB arrives in several chunks. A multi-byte character that crosses a chunk boundary turns into U+FFFD replacement characters.

I reproduced this with a `net` server that uses the same decode loop. A 60,045-byte JSON line that included `プロジェクト` and `ⓘ` arrived in 8 chunks and decoded with 12 replacement characters.

Envelopes with a filesystem listing, git context and the installed-tools chunk can pass 8 KB. A non-ASCII `queryText`, `cwd` or filename is then silently garbled before it reaches Claude. It also changes `cwd`, which the prewarm key and the `spawn` cwd depend on.

The phase fixed the same bug on the client side (`fetch-client.ts:122-125`, `setEncoding('utf8')`) but not here. Separately, `MAX_BUF_BYTES` compares `buf.length` (UTF-16 code units) plus `chunk.length` (bytes), which mixes units.
**Fix:**
```ts
const server = net.createServer((socket) => {
  let buf = '';
  socket.setEncoding('utf8'); // StringDecoder keeps split code points intact
  ...
  socket.on('data', (chunk: string) => {
    if (Buffer.byteLength(buf) + Buffer.byteLength(chunk) > MAX_BUF_BYTES) { ... }
    buf += chunk;
```

### WR-02: A stale prewarmed child that hangs (instead of exiting) uses the whole 25 s budget with no cold retry

**File:** `src/providers/claude-cli.ts:117-133`, `src/providers/claude-process.ts:387-395`
**Issue:** The cold retry only runs when `reason === 'exit-without-result'`. A warm child that never answers produces no failure until `budgetMs` (about 25 s) runs out. That covers two cases: no `init`, or a request stuck on a TCP connection that died during laptop sleep. The result is a `timeout` failure, which is never retried, and the user sees "Claude timed out".

The docstring names "a stale prewarm after a long idle or laptop sleep" as the case the retry is for, but the stall form of that case is not handled. Nothing bounds the time from writing the user line to `init` for a prewarmed child, even though research measured write to `init` at about 35 ms.
**Fix:** Give warm turns a short init deadline, for example `WARM_INIT_DEADLINE_MS = 1500`. If `init` has not arrived by then, terminate the child and reject with `exit-without-result`, or a new `stale-prewarm` reason that `isStalePrewarmFailure` accepts. The cold retry then runs inside the remaining budget:
```ts
if (prewarmed) {
  initTimer = setTimeout(() => {
    if (!sawInit && !settled) {
      terminateChild(child, killGraceMs);
      finish(() => reject(turnFailure('Command failed: claude', 'exit-without-result', false, {...})));
    }
  }, warmInitDeadlineMs);
  initTimer.unref();
}
```

### WR-03: Daemon shutdown retires the slot but leaves the pool enabled, so an in-flight query respawns a prewarm child

**File:** `src/cli/commands/daemon.ts:40-48`, `src/providers/claude-cli.ts:141-145`
**Issue:** `shutdown()` calls `retirePrewarmed()` and then `server.close()`, which waits for open connections. A fetch in flight on one of those connections finishes later, and its `finally { schedulePrewarm(spec) }` sees `enabled === true` and spawns a new idle `claude` (about 190 MB RSS). Then `process.exit(0)` runs.

The new child only goes away because the daemon's exit closes its stdin pipe. That is the opposite of what the shutdown comment says. Turn children that are in flight are also not tracked. Their budget and backstop timers die with the daemon, so a child that hangs after its `result` is orphaned for good. The `hang-after-result` fixture models exactly that child.
**Fix:** In `shutdown`, call `disablePrewarm()` (it retires and also sets `enabled = false`), not `retirePrewarmed()`. Optionally abort in-flight turns: keep a set of live connection AbortControllers in `startDaemonServer` and abort them on shutdown, so `runClaudeTurn` SIGTERMs its children while the daemon is still alive to send the SIGKILL.

### WR-04: The first streamed row alone decides whether to clear a query the user typed during loading

**File:** `src/ui/CandidateSelect.tsx:140-150`
**Issue:** The first-arrival branch clears `query` when `filterCandidates(candidates, query)` matches nothing. With streaming, `candidates` is a single row at that point, and `query` may be text the user typed while `thinking…` was shown, not just the lbuffer pre-filter.

Example: the user types `grep` while loading and the first row is `rg foo`. The typed filter is wiped, and the later `grep -r foo` rows appear unfiltered. Before 09.1 this decision used the full list, so a typed filter was only dropped when no candidate at all matched.

This contradicts the later-arrival rule in the same block ("the zero-match clear runs only while the user has not typed"; Pitfall 9).
**Fix:** Apply the same guard on first arrival:
```ts
if (
  candidates && candidates.length > 0 &&
  query === (initialQuery ?? '') &&
  filterCandidates(candidates, query).length === 0
) {
  setQuery('');
}
```

### WR-05: The later-arrival keep-highlight is undone by the `[query]` reset effect

**File:** `src/ui/CandidateSelect.tsx:154-171`, `src/ui/CandidateSelect.tsx:184-186`
**Issue:** When a later array triggers the zero-match clear (`setQuery('')`), the branch computes `nextIndex` from the highlighted row's `candidateKey` and sets it. After commit, `useEffect(() => setSelectedIndex(0), [query])` fires because `query` changed and resets the selection to 0.

So the D-06 "keep the highlighted row" guarantee fails exactly when the list changes most (final list versus streamed rows). The Zellij layout effect also runs once with the kept index and again with 0.
**Fix:** Do the query-driven reset at the place the user changes the query, not in an effect. Reset the index in the input handlers (`setQuery(q => q + input); setSelectedIndex(0)`) and in Backspace, and remove the `[query]` effect. Alternatively, track a ref flag set by the arrival branch so the effect skips the reset it caused.

### WR-06: The selection index is never clamped to >= 0, so -1 or NaN survives streamed arrivals

**File:** `src/ui/CandidateSelect.tsx:168`, `src/ui/CandidateSelect.tsx:291-300`
**Issue:** With an empty visible list, which is common while rows stream in under a typed filter, two keys corrupt the index:
- Down arrow sets `selectedIndex` to `(i + 1) % 0`, which is `NaN`.
- Up arrow sets it to `visible.length - 1`, which is `-1`.

When the next row arrives, the new branch computes `Math.min(selectedIndex, Math.max(0, visible.length - 1))`, and that keeps `NaN` or `-1`. No row is highlighted, ↑/↓ stay stuck on `NaN`, and Enter silently falls back to `visible[0]`, a row the user never saw selected.
**Fix:**
```ts
const clamped = Number.isFinite(selectedIndex) ? selectedIndex : 0;
const nextIndex = kept >= 0 ? kept : Math.max(0, Math.min(clamped, visible.length - 1));
```
Also make the arrow handlers return early when `visible.length === 0`.

### WR-07: SDK `max_tokens: 1024` is fixed while effort is now configurable; a truncated answer becomes a raw JSON fragment command

**File:** `src/providers/claude.ts:216-222`, `src/providers/claude.ts:239-242`
**Issue:** 09.1 makes effort configurable (`low` to `max`), and the SDK path leaves thinking adaptive by omitting `thinking`. Thinking tokens count against `max_tokens: 1024`. At `high`, `xhigh` or `max`, the visible text can be cut off before the first candidate object closes, and `stop_reason` is never checked.

`parseStrictCandidateList` then fails. Because no row streamed, `parseCandidates(text)` takes its "not JSON" branch and returns the truncated text, for example `[{"command": "find . -name`, as a selectable command. With no text at all, it returns `echo ""`.
**Fix:** Check `message.stop_reason === 'max_tokens'` and fail closed when nothing streamed. Either throw a clear "response truncated" error or return the streamed rows. Raise `max_tokens` with effort, or pin it high enough for adaptive thinking:
```ts
if (message.stop_reason === 'max_tokens' && streamed.length === 0) {
  throw new Error('QueQue: Claude response was truncated');
}
```

### WR-08: The `/tmp` socket is unauthenticated and squattable; a fake daemon is accepted and can now stream rows (pre-existing, CR-005)

**File:** `src/daemon/bootstrap.ts:222-231`, `src/daemon/server.ts:33-35`
**Issue:** `ensureDaemon` keeps any listener on `/tmp/qq-<uid>.sock` that answers `pong` with the three flags, or any listener that does not answer at all (`unknown`). Another local user can create that path in the world-writable `/tmp` before the victim's daemon starts. The victim's client then sends that listener the full envelope (cwd, query, git and filesystem context) and shows whatever `candidate` rows it returns. This phase extends the trust surface: streamed rows and a capability flag that is trivial to fake.

Commands are never executed automatically, so impact is limited to disclosure plus social engineering, but the risk is real on shared machines. The CR-005 TODO in `server.ts` still says "before Phase 4".
**Fix:** Before trusting the listener, check the socket's owner. `fs.lstatSync(socketPath)` must be a socket with `uid === process.getuid()`. On macOS, also check the peer with `LOCAL_PEERCRED` through a small native helper, or move the socket into a 0700 per-user directory such as `/tmp/qq-<uid>/` that you create with `mkdir` mode 0700 and whose owner you verify. Then add the session token planned in CR-005.

## Info

### IN-01: `hardError` maps every non-timeout, non-ENOENT failure to the "not authenticated" copy (dead branch)

**File:** `src/providers/claude-default.ts:69-80`
**Issue:** `if (isAuthFailure(error)) return new Error(D13_MESSAGE); return new Error(D13_MESSAGE);` has the same result on both branches. Now that `is_error` results carry the exact result text, an API overload or rate-limit `is_error`, an `invalid-result`, or a crash (`exit-without-result`) all tell the user "Claude is not authenticated. Run `claude /login`". CONTEXT keeps the 08 D-12/D-13 copy rules, so this follows the decision but misleads the user.
**Fix:** Delete the redundant `isAuthFailure` branch. Optionally add a generic "Claude request failed" copy for non-auth `is-error` and `invalid-result` reasons in a later phase.

### IN-02: The idle prewarm child pins the last query's cwd indefinitely

**File:** `src/providers/claude-prewarm.ts:119-175`
**Issue:** D-11 accepts keeping one process in memory, but the idle child also keeps its cwd open with no TTL. After `??` in `/Volumes/USB/...`, macOS reports the volume "in use" (by `claude`) until a query runs in another directory or the daemon stops. A directory that was deleted stays held in the same way.
**Fix:** Document this in D-11, or retire an idle child when its cwd stops existing (`fs.statSync` at take or refill), and/or add a long idle TTL.

### IN-03: `process.exit` in the client action drops pending debug-log writes and unref'd SIGKILL timers

**File:** `src/cli/main.ts:93`
**Issue:** `void appendDebugLog(...)` calls that are still pending, such as `'wrote llm result'` and `'fetch aborted'`, are lost. In the in-process fallback (no daemon), the `terminateChild` SIGKILL backstop is unref'd and never fires after `process.exit`. A `claude` child that ignored SIGTERM would be orphaned. Real Claude Code exits on SIGTERM, so this is low risk.
**Fix:** Await a short flush of the debug log before exiting, or accept this and note it in the D-15 comment.

### IN-04: The candidate scanner is not reset when a new `message_start` arrives within one turn

**File:** `src/providers/candidate-stream.ts:23-99`, `src/providers/claude-cli.ts:85-96`
**Issue:** If Claude Code retries an API call mid-stream, a second `message_start` follows partial deltas. The scanner keeps its `inString`, `depth` and `objectText` state across the boundary, and the retry's text is appended to the half-scanned object. That usually means no row streams. In rare cases a mixed object passes the schema. The strict final parse still decides the list.
**Fix:** Pass `message_start` stage events into the handler and recreate the scanner on each one.

**Confidence:** low. I did not confirm whether Claude Code re-emits deltas on retry.

### IN-05: A `[` in prose before the JSON array starts the scanner early and turns off streaming for the turn

**File:** `src/providers/candidate-stream.ts:58-63`, `src/providers/candidate-stream.ts:93-95`
**Issue:** Wrapper text such as `Here are [3] options:` starts the scanner at the first `[`, closes at `]` (depth 0), and sets `finished = true`. No row streams, and only the final list appears. Nothing wrong is shown, but the latency benefit is lost silently.
**Fix:** Start only at a `[` whose next non-space character is `{`, or reset `started` when the array closes with zero objects scanned.
