## Critical Issues

### CR-01: Backspace is silently dropped when it arrives in the same stdin read as earlier keystrokes (regression from the WR-05 fix)

**File:** `src/ui/CandidateSelect.tsx:240-247`
**Issue:** The WR-05 fix changed Backspace from an unconditional functional update to a guard on the render-closure `query`:

```ts
if (key.backspace) {
  if (query.length > 0) {          // closure value, not the pending state
    setQuery((q) => q.slice(0, -1));
    setSelectedIndex(0);
  }
  return;
}
```

Ink 7's `handleReadable` splits one stdin read into several keypress events and emits them synchronously in a loop. `ink/build/input-parser.js` turns `'a\x7f'` into `["a", "\x7f"]`, and `'ab\x7f\x7f'` into `["ab", "\x7f", "\x7f"]`. `useInput` runs the handler through `useEffectEvent`, which only sees the props and state of the last committed render. So the Backspace event still sees the query from before the `a` in the same read, and the guard drops it.

I verified this with a scratch real-Ink render, run outside the repo with a temporary vitest config and the same Writable/Readable TTY fakes as `candidate-select-layout.test.tsx`:
- pushing `'a\x7f'` in one chunk leaves `FILTER: a`
- pushing `'ab\x7f\x7f'` leaves `FILTER: ab`

The old code (`setQuery((q) => q.slice(0, -1))`, no guard) composed correctly with the pending update. Coalesced reads are normal under load: a busy Node event loop while rows stream in, the Zellij or tmux PTY, ssh, or Backspace auto-repeat. In those cases the visible filter disagrees with what the user typed, and the rows they see (and can accept with Enter) are filtered by text they deleted.

The existing tests did not catch this because `mounted.press()` sends one key per stdin push and waits for a flush.
**Fix:** Do not decide on closure state. Either reset unconditionally (Backspace on an empty query then moves the highlight to row 0, which is harmless), or keep the live query in a ref that the handlers update synchronously:

```ts
const queryRef = useRef('');
// …
if (key.backspace) {
  if (queryRef.current.length > 0) {
    queryRef.current = queryRef.current.slice(0, -1);
    setQuery(queryRef.current);
    setSelectedIndex(0);
  }
  return;
}
// …
if (input && !key.ctrl && !key.meta) {
  queryRef.current += input;
  setQuery(queryRef.current);
  setSelectedIndex(0);
  return;
}
```

If you use the ref, the arrow, Tab and Enter handlers should also filter on `queryRef.current`, since they have the same closure staleness. Add a real-hooks regression test that pushes `'ab\x7f\x7f'` as one chunk and expects the placeholder `FILTER: type to filter…`.

## Warnings

### WR-01: SDK fail-closed covers only `max_tokens`; a streaming `refusal` (or `pause_turn`) fragment still becomes a command

**File:** `src/providers/claude.ts:262-280`
**Issue:** The WR-07 fix branches on `message.stop_reason === 'max_tokens'` only. The installed SDK's `StopReason` is `'end_turn' | 'max_tokens' | 'stop_sequence' | 'tool_use' | 'pause_turn' | 'refusal'`. A streaming classifier `refusal` stops the output mid-generation in the same way. The text can be a fragment like `[{"command": "rm -rf`, or refusal prose. With no strict list and no streamed row, that reaches `parseCandidates`. `JSON.parse` fails, the prose fallback returns `[{ command: '[{"command": "rm -rf', explanation: '' }]`, and that fragment is offered for insertion into the shell buffer. This is the failure mode WR-07 set out to close. `pause_turn` gives the same incomplete-text result.
**Fix:** Treat every stop reason other than a normal finish as truncated:

```ts
const finishedNormally =
  message.stop_reason === 'end_turn' || message.stop_reason === 'stop_sequence';
// …
} else if (!finishedNormally) {
  const complete = completeCandidates(text);
  if (complete.length === 0) {
    void appendDebugLog('provider', 'response truncated', { model, stopReason: message.stop_reason });
    throw new Error(TRUNCATED_RESPONSE_MESSAGE);
  }
  finalList = complete;
}
```

Add a test with `stopReason: 'refusal'` and the fragment `[{"command": "find . -name`.

### WR-02: Daemon shutdown with no open connection exits at once, cancelling the SIGKILL backstop it just armed for the retired idle child

**File:** `src/cli/commands/daemon.ts:45-64` (with `src/providers/claude-prewarm.ts:84-105`)
**Issue:** `shutdownDaemon` calls `disablePrewarm()`, which runs `retireChild`: stdin EOF plus an **unref'd** SIGKILL timer after `SIGKILL_GRACE_MS`. It then waits for the grace only if `connections.size > 0`. On the common shutdown path (an idle daemon with an idle prewarmed child), `exit()` runs on `server.close`, so `process.exit(0)` happens long before the 1500 ms backstop. The backstop therefore never fires on daemon shutdown. That is exactly where it is needed: the `ignore-eof` fixture models a child that ignores EOF, and WR-02 models a child that hangs after laptop sleep. This contradicts the docstring ("Stops the daemon without leaving `claude` children behind").

The same applies to children whose connection is already closed but which still have a pending kill timer: a post-result child inside its `POST_RESULT_BACKSTOP_MS` window, or a `terminateChild` SIGKILL timer. The grace is keyed on sockets, not on live children.
**Fix:** Key the grace on running children, not on connections. For example, have `retirePrewarmed`/`disablePrewarm` return whether a running child was retired, and wait when either is true:

```ts
const retiredIdle = disablePrewarm(); // true when a running child was sent EOF
const inFlight = connections.size;
server.close(() => {
  if (inFlight === 0 && !retiredIdle) { exit(); return; }
  setTimeout(exit, graceMs);
});
```

A stricter fix is a small registry of children with pending kill timers (`claude-process.ts` `terminateChild`/`armBackstop`), and exiting once it is empty or the grace has passed. Add a test that uses the `ignore-eof` fixture, shuts down with no connection, and checks that the child is SIGKILLed before `exit` runs.

## Info

### IN-01: A second shutdown signal cuts the kill grace short

**File:** `src/cli/commands/daemon.ts:95-102`
**Issue:** SIGTERM and SIGINT each have their own `process.once` handler, so Ctrl-C followed by a SIGTERM (or the reverse) runs `shutdownDaemon` twice. On the second call, `server.close` on an already-closed server invokes its callback with `ERR_SERVER_NOT_RUNNING`. `connections.size` is 0 by then (the first call destroyed every socket), so `exit()` runs at once, during the first call's `graceMs` wait, and the SIGKILL backstops are lost.
**Fix:** Guard with a module-level `let shuttingDown = false;`. Return early if it is set, otherwise set it, then call `shutdownDaemon`.

### IN-02: The WR-01 byte-cap regression test only discriminates when the OS splits the write into small reads

**File:** `tests/daemon-fetch.test.ts` (`measures the 256 KB request limit in bytes, not UTF-16 code units`)
**Issue:** The old code compared `buf.length` (UTF-16 code units of earlier chunks) plus `chunk.length` (bytes of the current Buffer chunk). The test writes 1024 bytes, then the remaining ~269 KB in one `write`. If that write arrives as a single read (larger socket buffers, e.g. Linux defaults), the old check also rejects it (`1024 + ~269_000 > 262_144`), so the test passes without the fix. It only fails on the old code when the kernel delivers small (~8 KB) reads, as on macOS.
**Fix:** Write the payload in explicit small slices (for example 4 KB each, `setImmediate` between them), so the old code is forced to accumulate code units in `buf` on every platform.

### IN-03: The init deadline SIGTERMs a long-idle warm child in its pre-`init` window, which is unverified against credential refresh

**File:** `src/providers/claude-cli.ts:25-38`, `src/providers/claude-process.ts:414-436`
**Issue:** `claude-process.ts` deliberately avoids SIGTERM right after a `result`, because it "could cut off Claude Code's credential writes". The new `initDeadlineMs` SIGTERMs a prewarmed child that has been idle long (deadline 1500 ms), and the turn after a long idle or a sleep is the most likely moment for an OAuth token refresh. Nothing in the diff shows whether Claude Code refreshes before or after it emits `init`. If it refreshes first, a slow refresh is killed mid-write and then repeated by the cold retry. The fix report already marks WR-02 "requires human verification". This note narrows down what to verify.
**Fix:** In the UAT for WR-02, check (with `QQ_DEBUG` stage logs) that the first warm `??` after a sleep longer than the OAuth token lifetime logs `cli init` before any network-dependent delay. If it does not, raise `WARM_INIT_DEADLINE_MS` or move the deadline to the first `stream_event`.

Also of note, not a defect: when rows had already streamed before a `max_tokens` cut, `fetchCandidates` returns them as a complete list (`streamed.length > 0` wins), so the UI shows no `list may be incomplete` note (D-16). Consider surfacing that as `'partial'`.
