<objective>
Close the one verification gap left in phase 09.1: review finding CR-01, truth P9-6 in 09.1-VERIFICATION.md (D-09 filter editing, a 09.1-09 must-have).

Root cause (binding, from 09.1-REVIEW.md CR-01 and the verifier's independent reproduction). The WR-05 fix (a1eef40) made the Backspace branch of the `useInput` handler in `src/ui/CandidateSelect.tsx` (~l.240-247) decide on the render-closure query. Ink 7 parses one stdin read into several key events: `ab` plus two DEL bytes becomes `ab`, Backspace, Backspace. It runs them back to back through `useInput`, whose `useEffectEvent` holds the handler of the last committed render. React batches the state updates, so no render happens between those events. The Backspace events still see the query from before the read (empty), and the guard drops them. The verifier saw `FILTER: a` after `a` plus DEL in one chunk, and `FILTER: ab` after `ab` plus two DELs. The rows on screen are then filtered by text the user deleted, and Enter can insert from that list. The existing tests push one key per stdin read, so they pass.

The fix (Claude's discretion; the gap's `missing` list is a route, not a contract). Keep a `pendingInput` ref, a snapshot of the input state the key handlers have produced since the last committed render. Tag it with a `renderToken`, a new object identity created on every render. All handlers of one committed render share that token, so they honour the snapshot. After the next commit, the closure state already includes those edits and the snapshot is ignored. This is the review's ref route, widened from the query alone to the selection index and the Tab toggles. Enter, Tab and the arrows read the same three values from the render closure, so they have the same defect. Down then Enter in one read inserts row 0. Down, Tab, Backspace, Enter in one read inserts the untoggled row 0 command. Fixing only Backspace would leave that root cause in three sibling handlers.

Ink 7's input parser (node package `ink` 7.0.1, `splitBackspaceBytes`) splits a chunk only at escape sequences (arrows) and at DEL/BS bytes. `\r` and `\t` stay inside a text run so that pasted text survives. Typed letters followed by Enter or Tab with nothing between them, such as `smt` plus CR in one read, therefore reach the handler as one typed string, not as separate keys. That is Ink's paste rule and outside CR-01. Every coalesced sequence in this plan's tests puts an arrow or a DEL between a typed letter, a Tab and an Enter.

Why not drop the guard, the review's other option: it would make Backspace on an empty filter move the highlight to row 0. WR-05 kept that key a no-op on purpose (09.1-REVIEW-FIX.md: "matches the old effect"), and a mocked test pins it. It would also leave Enter, Tab and the arrows on stale state.

What does not change:
- the four useState calls and their order (the mocked suite indexes state by call order)
- the two useEffect calls (the mocked suite counts them)
- the render-phase arrival block, the layout effect, the render body and SearchInput
- run-foreground.ts and the zsh widget

Purpose: what the user sees in FILTER, the highlight and the inserted row depend only on which keys were pressed, not on how the terminal, Zellij, tmux, ssh or a busy event loop chunked them.
Output: a snapshot-based key handler in `src/ui/CandidateSelect.tsx`; real-Ink and mocked regressions that fail before the fix; CR-01 marked fixed; OpenWolf and buglog records.
</objective>
