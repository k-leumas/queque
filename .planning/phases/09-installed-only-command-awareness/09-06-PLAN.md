<objective>
Close UAT gap G-09-7 (major). In a Zellij floating pane, `??` sometimes shows the candidates and then shrinks to an empty modal: only the explanation tail, legend and controls stay visible. The debug session proved the failure needs two conditions together, and that a third makes it permanent:

1. **Stale height.** On candidate arrival, CandidateSelect's layout effect first reports the render that still filters by `initialQuery` (the lbuffer, which matches no command). That is the "no matches" estimate: 7 lines, pane height 9. The reset effect then clears the query and the full list is reported (22 lines, height 24).
2. **Unordered resizes.** `syncZellijFloatingPaneHeight` starts one detached `zellij action` per call. Zellij applies them in completion order, so the height-9 shrink can land last.
3. **No repaint.** Ink's `/dev/tty` `tty.WriteStream` never emits 'resize', so nothing recovers.

**Mechanism chosen** (both conditions removed at their source):

- **Task 1, render-phase arrival reset.** CandidateSelect remembers the candidates array it last reset for, in a fourth `useState` called `prevCandidates`. When the prop differs, the component resets during render: selection, Tab toggles, and a non-matching lbuffer query. This is React's documented "adjust state when a prop changes" pattern. React discards that render and retries before committing, so the layout effect never runs for the stale `initialQuery` render, and the "no matches" frame is never drawn. A planning probe confirmed it: real Ink reported `[6, 11]` before the change and `[11]` after, and the no-match frame was no longer written.
- **Task 2, serialized latest-wins resize queue.** Only one `zellij action` runs at a time. A height requested while one runs replaces any earlier waiting height, and the newest waiting height is spawned when the running action exits. A spawn error, or a settle timeout that kills a hung action, also releases the slot. This removes the race for every source of rapid height changes, not only candidate arrival: fast typing, Backspace, and arrow keys across a destructive row's ⚠ footer.

**Not done: wiring SIGWINCH to the `/dev/tty` stream** (marked optional in the gap). Three reasons:

1. Once 1 and 2 are removed, the pane's final height always equals the newest estimate of what Ink has drawn, so no repaint is needed. The debug falsification run without the stale estimate kept the list 10/10.
2. Ink's `resized()` only clears when the width shrinks, and it skips a write when the frame is unchanged. So a 'resize' event would not restore lines Zellij has already pushed into pane scrollback.
3. It would change Ink's behaviour on every terminal-window resize in the inline (non-Zellij) path, which is new behaviour beyond this gap.

Purpose: `??` inside Zellij shows the candidates and keeps them (UAT test 7, SC-3's "shown … remains selectable"). The bug predates Phase 9 (99adc79) and hit about 25–50% of runs, with or without tool awareness.

Output: render-phase reset in `src/ui/CandidateSelect.tsx`, serialized queue in `src/client/zellij-pane-resize.ts`, a new real-hooks test file, ordering tests, and OpenWolf, buglog and debug-session records.
