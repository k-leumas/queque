# Phase 3.2 Plan Review

## Overall Summary

The wave ordering is sound: test-first, then Node-side transport changes, then the shell rewrite. The Node plan is relatively small and aligned with the current code seams in `src/client/result-writer.ts` and `src/client/run-foreground.ts`. The shell plan is where most of the real risk sits. The proposed FIFO flow does remove the inline TTY hack, but the current widget design has several blocking and lifecycle assumptions that are unsafe in `zsh`, and those issues are significant enough that I would not approve Wave 3 as written.

---

## PLAN 01 — Wave 1: Test Foundation

### Summary

This is a reasonable red-first setup and it targets the right seams, especially `writeShellResult` and `/dev/tty` gating. The weakness is that too much of the widget coverage is still text-grep based rather than behavior based, so the tests will miss the hardest failures introduced by the FIFO rewrite.

### Strengths

- Covers the two real transport changes: FIFO-aware result writing and Zellij-aware foreground rendering.
- Preserves the current `fs/promises` mock strategy instead of over-mocking file I/O globally.
- Calls out the `ZELLIJ=0` detail explicitly, which matters for shell detection.
- Keeps the first wave narrow and achievable.

### Concerns

- `MEDIUM`: The widget tests mostly grep source text. They will pass even if the FIFO flow hangs, leaks traps, or mishandles launch failures.
- `MEDIUM`: There is no test for the new failure mode where the shell times out or exits first and the client later fails to write to the FIFO.
- `LOW`: Shell and Node Zellij detection semantics can drift, and the planned tests do not pin that down clearly for `unset` vs `""` vs `"0"`.

### Suggestions

- Add one behavior-level shell test that stubs `zellij` and `qq` on `PATH`, drives the widget path, and asserts buffer restoration/replacement plus cleanup.
- Add a unit test for FIFO write failure handling in `writeShellResult` or its caller.
- Add one explicit detection matrix test for `ZELLIJ` values: unset, empty string, and `0`.

### Risk Assessment

`MEDIUM`. Good start, but not yet strong enough to de-risk the shell rewrite.

## PLAN 02 — Wave 2: Node.js Production Implementation

### Summary

This plan is mostly well-scoped and matches the current implementation. The FIFO-aware writer is the correct transport change, and the `run-foreground.ts` branch is small enough to be low churn. The main gap is error semantics once the shell-side FIFO reader disappears or times out.

### Strengths

- Changes are localized to the two correct files.
- Direct FIFO write is the right fix; `rename()` would indeed destroy the FIFO path.
- The Zellij branch removes the scroll hack cleanly instead of layering another rendering mode on top.
- Keeping `ensureDaemon` unconditional is pragmatic and consistent with startup-latency goals.

### Concerns

- `MEDIUM`: `process.env['ZELLIJ'] !== undefined` does not match the shell plan's `[[ -z "$ZELLIJ" ]]` behavior. An empty string would diverge.
- `MEDIUM`: The plan does not define what happens if direct FIFO write fails with `EPIPE`, `ENOENT`, or similar after the shell side has already canceled/cleaned up.
- `LOW`: `render({})` relying on inherited stdio is probably fine in Zellij, but it is still an assumption that deserves one real verification point.

### Suggestions

- Align Zellij detection semantics across shell and Node. A simple non-empty check is safer than only checking for `undefined`.
- Define FIFO write failure behavior explicitly: log it, exit cleanly, and do not attempt fallback mutation.
- Add one assertion around the Zellij branch so `/dev/tty` is truly skipped and Ink is using default stdio.

### Risk Assessment

`MEDIUM`. The implementation is small and likely workable, but it needs explicit failure behavior for broken FIFOs.

## PLAN 03 — Wave 3: ZSH Widget Rewrite + Manual Verification

### Summary

This plan achieves the intended UX direction, but it is the weakest part of the proposal technically. The FIFO lifecycle, timeout model, and trap strategy are not safe as written. The biggest issue is that the proposed `read -t 30 < "$fifo_path"` does not actually guarantee the widget won't block indefinitely, and the 30-second timeout is itself a UX regression if the user takes longer than 30 seconds in the pane.

### Strengths

- Removes the old `/dev/tty` redirection path completely, which is consistent with the phase goal.
- Preserves the existing request-file contract and helper structure where possible.
- Manual verification gates the highest-risk user flow instead of trusting tests alone.
- Keeps Zellij as a hard requirement rather than adding fallback complexity.

### Concerns

- `HIGH`: `read -r -t 30 result < "$fifo_path"` can still hang before `read` starts, because opening a FIFO for reading may block until a writer connects.
- `HIGH`: A 30-second timeout is not a valid session model for an interactive picker. If the user spends more than 30 seconds in the pane, the widget cancels and cleans up while the client is still running.
- `HIGH`: `mktemp -u` is a TOCTOU race. The sticky bit does not make that safe.
- `MEDIUM`: `trap '_qq_cleanup' EXIT ERR INT` in a sourced interactive shell risks clobbering user trap state.
- `MEDIUM`: Step 9 duplicates `_qq_apply_result` behavior instead of reusing the tested helper, which invites drift.
- `MEDIUM`: Launch/setup failure paths for `mktemp`, `mkfifo`, `zellij run`, and `jq` are not fully specified after the buffer has already been mutated.
- `LOW`: Hard-coded `80x24` is acceptable for MVP, but it may be cramped on small terminals or for verbose candidate explanations.

### Suggestions

- Replace `mktemp -u` with `mktemp -d` and create the FIFO inside that directory.
- Remove the 30-second session timeout. If you want a safety valve, make it about launch/handshake failure, not user think time.
- Do not rely on `< "$fifo_path"` plus `read -t` as the anti-hang mechanism; solve the FIFO-open blocking problem explicitly.
- Avoid global trap clobbering. Use a local cleanup pattern that does not overwrite user shell traps, or save and restore the old handlers.
- Reuse `_qq_apply_result` instead of reimplementing result parsing in the widget.
- Add explicit failure handling that restores the original buffer and shows a `zle -M` message when setup fails.

### Risk Assessment

`HIGH`. The UX intent is correct, but the shell control-flow design needs revision before implementation.

## Final Assessment

I would approve Wave 1 and most of Wave 2 with small changes. I would not approve Wave 3 as written. The phase goal is still achievable, but the widget plan should be revised around three points before coding:

- safe FIFO creation
- non-brittle blocking/handshake behavior
- cleanup that does not depend on global trap side effects

If those are corrected, the phase stays appropriately scoped for the MVP.
