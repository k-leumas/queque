<objective>
Fix the top `queque › …` line being clipped after the Zellij floating pane resizes to fit the modal.

**Root cause (confirmed by the G-09-7 debug session, Evidence 10:02Z, and by a planning probe).** Ink 7 runs in interactive mode, and when a frame is shorter than the rows Ink believes it has, it writes the frame as output plus `'\n'` (`renderInteractiveFrame` in node_modules/ink/build/ink.js, around lines 685-735). That leaves the cursor on its own row below the frame, so an N-line frame takes N + 1 PTY rows. `resolveZellijPaneHeight` gives the pane N + 2 rows, and the 2 are the border and title (`ZELLIJ_FLOATING_FRAME_LINES`), so only N PTY rows are left. That is one row short. The terminal scrolls the top row, which is the `queque ›` header, into pane scrollback: the frame title shows `SCROLL: 0/1` and a blank cursor row sits at the bottom. The probe used a real Ink render, 78x22 TTY fakes and the z3 fixtures from tests/candidate-select-layout.test.tsx. Layout reports were 15, 17 and 8 lines (plain, flagged, smt2 pre-filter). Ink's last frame took 16, 18 and 9 rows. The pane currently gives 15, 17 and 8 PTY rows, so it is always one row short. This happens on every run whose final height is below the cap. It is separate from the G-09-7 race, which 09-06 fixed.

**Chosen fix: direction (b), pane headroom.** Add a module-private named layout constant `INK_TRAILING_CURSOR_ROWS = 1` next to `ZELLIJ_FLOATING_FRAME_LINES` in src/client/zellij-pane-resize.ts. `resolveZellijPaneHeight` then returns content + frame rows + cursor row, with the same minimum of 6 and the same QQ_PANE_HEIGHT cap. This follows the user rule: a purely presentational offset belongs in a named layout constant, not in logic.

Why (b) is robust:
- **Below the cap:** the pane's PTY rows are exactly what Ink takes. When Zellij shrinks the pane, the cursor row is never below the new bottom, so nothing is pushed into scrollback.
- **At the cap:** the widget launches the pane at QQ_PANE_HEIGHT and exports that value (shell/zsh/queque.zsh around lines 284-292). Ink reads its row count once at launch (QQ_PANE_HEIGHT − 2), and that count is correct whenever the pane is at full height. A frame one row shorter than the pane fits exactly with its cursor row. A frame exactly as tall as the pane takes Ink's fullscreen path, which writes no trailing newline, so it also fits. `min()` absorbs the extra row.
- **Growth:** if Ink draws a taller frame before the grow lands, the overflow goes into scrollback, and Zellij pulls those lines back when the pane grows. Debug run f0-2 went 24 → 9 → 22 and left only the single cursor-row line in scrollback. With the headroom, nothing is left behind.
- Only the Zellij sizing changes. The inline path, which has no resize callback, and the 09-06 queue semantics are untouched.

Why not (a), forwarding the window-resize signal to the /dev/tty stream, or (c), both:
- The clip happens at the moment Zellij shrinks the pane under a frame whose cursor row is below the new bottom. No resize notification could reach Ink before that, so updating its rows afterwards cannot prevent it.
- Ink's `resized()` only clears the screen when the width shrinks, and it skips writing a frame that has not changed, so it cannot pull the header back out of scrollback.
- With (b), Ink's row count only affects its decisions at the cap, where it is already correct.
- It would change Ink's behaviour on every terminal resize in the inline path. The 09-06 decision log (cerebrum) already rejected it for these reasons.

Purpose: the header stays visible on every Zellij run, while keeping every G-09-7 guarantee.
Output: one constant plus the resolveZellijPaneHeight change, a real-Ink regression test and a unit mapping test, updated queue-test heights, OpenWolf records, and a live Zellij human check.
</objective>
