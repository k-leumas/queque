## Code-grounded facts (observed by the planner on 2026-10-17; re-check each one against the cited code before writing it into the README)

F1 — Provider choice. The source is src/providers/claude-default.ts: `claudeDefaultAdapter.fetchCandidates`, `lookupApiKey`.
- `lookupApiKey()` returns the first usable secret. It checks `process.env.ANTHROPIC_API_KEY` first, then `readEnvValueFromDotEnvLocal('ANTHROPIC_API_KEY')`. A value that is empty or only whitespace counts as missing (`usableSecret`).
- If a key is found, the adapter returns the Anthropic SDK path directly and there is no `claude -p` fallback.
- If no key is found, it runs `fetchClaudeCliCandidates`, which is `claude -p` with Claude Code's own login.
- A `claude -p` failure is not rescued by the SDK.
- The failure copy users see:
  - D13_MESSAGE: "QueQue: Claude is not authenticated. Run `claude /login`, or set ANTHROPIC_API_KEY in the environment or .env.local."
  - ENOENT_MESSAGE, when `claude` is not on PATH: adds "Install Claude Code".
  - TIMEOUT_MESSAGE.

F2 — claude -p argv. The source is src/providers/claude-cli.ts `buildClaudeCliArgv`.
- `-p`, stream-json in and out, `--effort <config effort>`, `--safe-mode`, `--tools ''` (no tools), `--no-session-persistence`, and a `--system-prompt`.
- No model flag, so Claude Code's own default model is used and QQ_MODEL does not apply.
- Never `--bare`, because that skips Keychain/OAuth for `/login` users.
- The daemon keeps one warm `claude` process ready (src/providers/claude-prewarm.ts). The first `claude -p` query after the daemon starts runs cold (src/cli/commands/daemon.ts comment).

F3 — SDK model. The source is src/providers/claude.ts.
- `DEFAULT_MODEL = 'claude-sonnet-5'`.
- `resolveModel()` uses `process.env.QQ_MODEL`, then `.env.local` QQ_MODEL, then the default.
- `effort` goes out as `output_config.effort`. It is left out for models that do not support effort. The README config table already says this; keep it.

F4 — NOT shipped. `detectProvider()` in src/providers/detect.ts is not on the runtime path. Only src/providers/index.ts re-exports it, and src/providers/resolver.ts maps every detected kind to the Claude composite. ROADMAP Phase 8 plans 08-03..08-06 (provider pin, other vendors, `qq init provider`) are unchecked.
- The README must not describe detect.ts behaviour as a QueQue feature. That covers its non-Claude providers and its CLAUDE_CODE_OAUTH_TOKEN / ANTHROPIC_AUTH_TOKEN checks.
- On the `claude -p` path, QueQue just runs `claude`. Whatever login `claude` already has is what gets used.

F5 — Daemon lifecycle.
- shell/zsh/queque.zsh `_qq_prewarm_daemon` runs `qq daemon --ensure` in a background subshell. This happens while the script is being sourced in an interactive shell, so normally while ~/.zshrc loads.
- src/client/run-foreground.ts:165 also calls `ensureDaemon` on every `??`.
- src/daemon/bootstrap.ts `spawnDaemon` sets no cwd and no env. The daemon therefore inherits the environment and working directory of the process that spawned it. It then serves every terminal over `/tmp/qq-<uid>.sock` (src/shared/socket-path.ts).
- Consequence (a): ANTHROPIC_API_KEY and QQ_MODEL must be exported in ~/.zshrc before the QueQue source line. `qq init zsh` appends that line at the end of the file, so an export added below it later is not seen by a daemon prewarmed at shell start.
- Consequence (b): `.env.local` is searched upward from the daemon's start directory, not from the directory of each `??`. The result is cached for the life of the process (src/shared/env-file.ts `envCache`). The current README's per-project `.env.local` wording is therefore inaccurate for the normal daemon path. Only the cold in-process fallback, used when the daemon is unreachable, searches from the client's cwd.
- Consequence (c): config.json is read once per process (`loadQqConfig` cache, src/shared/qq-config.ts).
- Changing any of these needs a daemon restart.
- Restart: the daemon handles SIGTERM gracefully (src/cli/commands/daemon.ts `shutdownDaemon`). Live daemon argv seen with `pgrep -fl` is `node …/dist/cli/app.js daemon --socket /tmp/qq-501.sock`. Matching restart guidance: `pkill -f 'daemon --socket /tmp/qq-'`, then run `qq daemon --ensure` in a shell that has the new environment. The next `??` would also respawn the daemon.

F6 — Install command. The source is src/cli/commands/init.ts `initCommand`.
- It appends `# queque shell integration` and `source "<script>"` to ~/.zshrc itself, then prints a status line on stdout.
- If the integration is already there, it prints to stderr and exits 0.
- The README currently pipes that stdout into ~/.zshrc as well. That writes the status line into ~/.zshrc, and it fails as a command when sourced.
- The correct form is `qq init zsh && source ~/.zshrc`. The README uses the broken form in two places: the NOTE box and the npm details block.

F7 — Requirements.
- tsup.config.ts has `target: 'node24'`, `.nvmrc` is `24.14.1`, and every CI workflow reads `.nvmrc`. So the README's Node 20 floor is stale and should become "Node.js 24 or newer".
- jq is still needed: shell/zsh/queque.zsh parses results with it, and the Homebrew formula depends on it.
- zsh is required.
- Claude Code (`claude` on PATH, signed in) is needed only for the no-API-key path.

F8 — Installed-tool awareness (Phase 9).
- The zsh widget writes the names in `$commands`, `$builtins`, and functions plus aliases into the per-request session directory. It can be switched off with `QQ_TOOL_AWARENESS=0` (shell/zsh/queque.zsh `_qq_write_tool_handoff`).
- The picker marks a candidate whose command words zsh cannot resolve with ⓘ and a legend, and the row stays selectable (src/ui/CandidateSelect.tsx; see `missingToolsLegend` for the exact copy).
- On a flagged row, Tab or Shift+Tab toggles an install form for brew, apt, dnf or pacman (src/shared/tool-awareness.ts `InstallerId`).
- The full inventory stays in the foreground client. Only installed names that are also in the shipped public catalog (src/shared/tool-catalog.ts) reach the model. They go into the system prompt as a "Notable command-line tools installed on this machine" line (src/providers/steering.ts `buildSteeringText`).

F9 — What is sent. The source is src/providers/claude.ts `buildPrompt`, used by both paths.
- After `filterContextEnvelope`, the prompt carries `cwd`, `queryText`, `platform` (the OS name), `shellName` (zsh), `versionControl` (the git chunk) and `filesystem` (filename hints).
- The system prompt adds the catalog tool-name steering from F8.

F10 — Picker behaviour (09.1, see CHANGELOG.md Unreleased and src/ui/CandidateSelect.tsx).
- Rows stream in as they arrive, and one can be picked before the rest have loaded.
- FILTER opens empty, and the typed text shows as the dim `queque ›` header.
- Typing during `thinking…` filters the list.
- Esc cancels the provider request and restores the buffer.
- Destructive matches show the warn-only ⚠ "review carefully — this command may be destructive" copy.
- Enter inserts exactly the text shown, and nothing is ever executed.
