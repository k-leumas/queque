<objective>
Keep the Zellij floating pane at its full-list height while the user filters, instead of shrinking it.

**User report (verbatim):** "when filtering using smt, the modal shrinks but shows an empty square --- i'd alsmost rather the modal container didn't shirnk at all". The user accepted this recommendation: size the pane when candidates arrive, and hold that height while the user filters.

**Root cause (confirmed by a planning probe).** The probe was a transient real-Ink vitest run using the z3 fixtures and the 78x22 TTY fakes from tests/candidate-select-layout.test.tsx. The file was removed afterwards and the tree is clean. CandidateSelect's layout effect reports `estimateCandidateSelectLines` for the current filtered state on every query change, and `syncZellijFloatingPaneHeight` turns each new value into a resize. With `show me how to use z3`, the reports were `[15,15,8,8,8,15,15]` for arrival, `s`, `sm`, `smt`, then three Backspaces. The spawned heights were `18,11,18`: a shrink on `sm` and a grow on the way back. Each shrink and grow is a detached `zellij action` that takes about 100-420 ms. During that time the pane and Ink's frame disagree, and that is where the empty area shows.

**Decisions made in this plan (the orchestrator asked for these to be decided and documented):**

1. **Scope: the Zellij pane path only.** The hold lives in what CandidateSelect reports through `onLayoutLinesChange`. run-foreground.ts passes that callback only when `inZellij`, and outside Zellij it passes undefined. So the inline path is untouched: Ink's frame still shrinks naturally (log-update erases the extra rows), and the fixed inline scroll reserve `MODAL_VIEWPORT_LINES` (18) is unchanged. Holding the inline reserve would mean padding Ink's frame with blank rows in a plain terminal. Nobody asked for that, and it would change the inline layout that the user did not report. run-foreground.ts, zellij-pane-resize.ts (the 09-06 queue and the e43 `INK_TRAILING_CURSOR_ROWS` headroom) and `MODAL_VIEWPORT_LINES` are not edited.
2. **Arrival sizes the pane for the unfiltered list.** The pane gets the height of the frame the user would see after clearing the filter: query `''`, row 0 selected (the `useEffect([query])` reset selects row 0), and the current Tab toggles (hidden rows keep their toggle). This applies even when the lbuffer pre-filters on arrival (e.g. `smt2`), so clearing the filter never needs a grow. Tests (d) and (e)-smt2 change on purpose because of this.
3. **The hold is a per-list high-water mark.** While the same `candidates` array is shown, the reported lines are `max(previous held, current frame estimate, unfiltered frame estimate)`. They never go down. This covers filtering and Backspace. It also covers a case a stateless max would miss: the user arrows onto a ⚠ row (frame +2), then types a filter, and the selection resets to row 0. That would otherwise shrink the pane mid-filter. The pane still grows when a frame becomes taller than the held height (⚠ footer, wrapped install form after Tab), so the e43 invariant holds (pane PTY rows >= Ink rows). It never shrinks for that list, which matches "didn't shrink at all". The only height changes left inside one list are grows.
4. **A re-query may resize.** The hold is keyed by the identity of the `candidates` array. A new array resets it, and the pane is sized for the new list: one resize, up or down. Production fetches candidates once per `??` client today, so this happens only for a future re-query path, but it is decided and tested (g). The loading-to-arrival shrink (the pane launches at QQ_PANE_HEIGHT) is unchanged.

**Why this is safe for Ink's drawing (verified in the probe and in node_modules/ink/build/log-update.js).** Ink 7 writes each interactive frame inside a synchronized-output pair (`ESC[?2026h` … `ESC[?2026l`). The frame is `eraseLines(previousLineCount)` (`ESC[2K` + `ESC[1A`, repeated, then `ESC[G`) followed by the new frame text. A shorter frame therefore erases every row of the taller one, including the cursor row, and redraws from the frame's top row. The pane is held at or above every frame since arrival, so nothing scrolls and the header stays on row 0. Test (f) checks this with a small screen replay of Ink's actual writes rather than trusting the source reading. Backspace is `\x7f`, which Ink 7's parse-keypress maps to `key.backspace`.

**React constraints (cerebrum Do-Not-Repeat, G-09-7).** No state is set in an effect. The hold is a `useRef`, written inside the existing layout effect, and it never causes a render. The render-phase `prevCandidates` arrival reset is untouched, so the first committed frame for new candidates is already reset when the effect reads the ref.

No new presentational offset is introduced. The hold is a max of existing estimates. `ZELLIJ_FLOATING_FRAME_LINES`, `INK_TRAILING_CURSOR_ROWS` and `MIN_PANE_HEIGHT` stay the only pane row constants.

Purpose: filtering in the Zellij modal no longer resizes the pane, so the empty area can't appear and the modal stops jumping while the user types.
Output: `heldPaneLines` in src/ui/modal-layout.ts, a per-list pane hold in src/ui/CandidateSelect.tsx, real-Ink regressions (f)/(g) with a screen replay, unit tests, updated (d)/(e) expectations, and OpenWolf records.
</objective>
