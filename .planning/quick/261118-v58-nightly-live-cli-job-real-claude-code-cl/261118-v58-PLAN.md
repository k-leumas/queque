<objective>
Add a nightly `live-cli` job that runs qq's Claude Code CLI provider path against the real `claude`
binary (the latest @anthropic-ai/claude-code from npm). It reuses the contract checks from the
existing SDK live test, so a change in Claude Code's stream-json events or flags turns the nightly
red. Today only tests/fixtures/fake-claude-stream.mjs exercises src/providers/claude-cli.ts,
claude-prewarm.ts and stream-json.ts.

Purpose: catch drift in the real Claude Code CLI path within a day, without blocking merges.
Output: a shared live harness (tests/live/live-daemon.ts), a new tests/live/cli-contract.live.ts,
sdk-contract.live.ts rebuilt on the harness with the same assertions, and nightly.yml with a
`live-cli` job while `live` keeps testing only the SDK path.

Provider pin finding (orchestrator asked us to investigate): qq has no setting that forces
`claude -p` while an API key is usable. A provider.json `{"provider":"claude"}` pin resolves to the
same SDK-first composite (resolveProviderAdapter -> resolveClaudeDefaultAdapter), and
claudeCliAdapter is unregistered. The only supported route to the CLI path is the product's own
selection rule: no usable ANTHROPIC_API_KEY in qq's env or ~/.env.local means `claude -p`. That is
exactly the situation of a `/login` user. So the CLI test hides the key from the daemon env and
lets Claude Code authenticate the way Claude Code supports, through an `apiKeyHelper` in the
temp-HOME user settings. src/ is not touched and no test-only backdoor is added.
Facts we checked (2026-11-18):
- claude 2.1.311 runs the user-settings apiKeyHelper under the `--safe-mode` flag that qq passes,
  with HOME pointing at a temp dir.
- npm `@anthropic-ai/claude-code` latest is 2.1.328, its bin is `claude` and it needs node >=22.
</objective>

- src/contracts/candidates.ts: commandCandidateSchema, candidateListSchema (array min 1 max 5)

- 'sdk path': claude-default.ts, written when the SDK branch runs (a usable key)
- 'claude-cli path': claude-default.ts, written only when a `claude -p` turn FAILED (not on abort)
- 'cli result', 'cli timed out', 'cli init timed out': claude-cli.ts STAGE_LOG_NAMES
- 'prewarm hit', 'prewarm miss', 'prewarm retry cold': claude-cli.ts
- 'prewarm spawned', 'prewarm spawn failed', 'prewarm error': claude-prewarm.ts
- 'response truncated': claude.ts finalCandidateList (shared by the CLI path); 'request failed': claude.ts SDK path

Prewarm facts (src/providers/claude-prewarm.ts, claude-cli.ts):
- The daemon command calls enablePrewarm(). A fresh daemon's first turn is a cold miss.
- fetchClaudeCliCandidates calls schedulePrewarm(spec) in its `finally`, before its promise
  settles. So by the time the client reads the final `candidates` line, an idle child for this
  cwd and argv has been spawned.
- The pool key is a sha256 of {command, cwd, argv}. argv embeds buildSystemPrompt(envelope),
  which depends only on the installed-tools extra (not on the timestamp or the query). A second
  request with the same cwd and `extras: []` therefore takes the prewarmed child (`prewarm hit`).

Claude Code auth precedence (code.claude.com/docs/en/authentication): ANTHROPIC_AUTH_TOKEN >
ANTHROPIC_API_KEY > apiKeyHelper > CLAUDE_CODE_OAUTH_TOKEN > /login. So the daemon env must also
drop ANTHROPIC_AUTH_TOKEN and CLAUDE_CODE_OAUTH_TOKEN, so that a developer's local tokens cannot
outrank the helper.
