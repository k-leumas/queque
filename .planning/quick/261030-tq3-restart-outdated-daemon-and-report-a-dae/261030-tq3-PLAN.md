<objective>
Fix bug-473 in code. A daemon from an older qq build kept running after an upgrade or rebuild. It
ignored the new `telemetry-event` / `telemetry-show` IPC kinds, so events were dropped and
`qq telemetry show` claimed "daemon not running" while a daemon was listening.

Requirements, numbered as in the task description:
- R1: the client notices a daemon from another build and replaces it (graceful shutdown, then a
  fresh daemon). The same-build path gets no extra latency, and the shell buffer is never touched.
- R2: CLI commands that use the requestDaemon no-reply path tell "no daemon listening" apart from
  "daemon connected but did not answer", and print an accurate, actionable message for the latter.
- R3: focused vitest regression tests for both, with pinned contract tests updated deliberately.

Signal choice (R1, justified). The signal is a build id, `__QUEQUE_BUILD_ID__`, injected by tsup
`define` in the same way as `__QUEQUE_TELEMETRY_KEY__`. Its value is `<package version>+<git short
commit>.<build time in base 36>`, computed once each time tsup evaluates its config.
- The semver alone fails the user's real case. A dev rebuild (`node $QQ_DEV_ROOT/dist/cli/main.js`)
  keeps package.json's version, so the stale daemon would never restart.
- The commit alone misses uncommitted rebuilds. It is also 'unknown' in Homebrew source builds (no
  .git), so two different Homebrew releases would compare equal.
- A per-build id changes on every `pnpm build` and every release build. Because a daemon is always
  spawned from the same app.js as the client that spawned it, an equal id means equal code.
- The cost is one daemon respawn after each rebuild or upgrade: the warm prewarm `claude -p` child is
  lost once. That restart is exactly the fix, because a daemon left running after a rebuild runs stale
  code. This deliberately supersedes the Phase 9 note in the cerebrum Decision Log (2026-10-08), which
  deferred build-hash-in-pong because it restarts on dev rebuilds.
- Known limit: `tsup --watch` evaluates the config once, so watch rebuilds share one id. `pnpm build`
  (which `pnpm dev:restart` runs) always gets a fresh one.
- Version and commit are part of the id so that debug-log lines can be read by a human.

Compatibility. Old daemons' pongs have no `build`. zod keeps the key absent, and an absent build
counts as "another build". The only way to keep a daemon is a pong that parses and whose build equals
the client's. The existing four capability flags stay as a second guard (fix, don't delete). The
"no reply = keep" rule stays.

Restart path. ensureDaemon's existing 'no' branch already calls replaceStaleListener. That is the same
graceful `{kind:'shutdown'}` plus lsof backstop that restartDaemon (`qq init provider`) uses, so no
new shutdown code is written. Old daemons support shutdown since WR-07. The same restartDaemon is
exposed as `qq daemon --restart`, so the R2 message has one command that works for any silent
daemon. `qq daemon --ensure` keeps a listener that never answers the ping, so it cannot be the hint.

No change is needed in shell/zsh/queque.zsh or src/client/run-foreground.ts:
- `_qq_prewarm_daemon` already runs `daemon --ensure` in a backgrounded subshell with output on
  /dev/null.
- run-foreground already awaits ensureDaemon before Ink and catches its failures.
- After an upgrade, the one-time replacement shows as the widget's instant `thinking…` frame.

Output: build-id signal end to end, `qq daemon --restart`, accurate telemetry no-reply copy, regression
tests, docs, and .wolf bookkeeping. That is three commits, each passing commitlint. Do not push.
Expected time: about 45-60 minutes (Task 1 about 25 min, Task 2 about 10 min, Task 3 about 15 min,
final E2E about 5 min).
</objective>
